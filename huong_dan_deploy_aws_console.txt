2. NHIỆM VỤ CHI TIẾT & BẢN CHẤT CỦA TỪNG LAYER TRONG HỆ THỐNG ENTERPRISE
================================================================================

1. CLOUDFLARE EDGE & WAF LAYER:
   - "Lá chắn thép đầu tiên" (First Line of Defense) đặt trước toàn bộ hạ tầng AWS.
   - Anycast DNS siêu tốc: Phân giải tên miền toàn cầu trong 10ms.
   - Ẩn giấu 100% địa chỉ IP thật và CNAME của AWS Application Load Balancer.
   - Web Application Firewall (WAF): Chặn các cuộc tấn công DDoS Layer 3/4 và Layer 7,
     tự động chặn bot cào dữ liệu ghế và các cuộc tấn công SQL Injection, XSS.

2. INGRESS & LOAD BALANCING LAYER (AWS ALB + ACM):
   - Phân phối tải thông minh (Round-Robin / Least Outstanding Requests) tới các cụm máy chủ.
   - Quản lý chứng chỉ SSL/TLS tự động gia hạn thông qua AWS Certificate Manager (ACM).
   - Health Check: Liên tục kiểm tra nhịp tim (Heartbeat) của các container. Nếu một máy chủ bị treo,
     ALB tự động ngắt kết nối và điều phối khách sang máy chủ còn lại mà không gây gián đoạn phiên đặt vé.

3. DMZ TIER 1 - DUAL NAT GATEWAY (High-Availability Outbound):
   - Đặt 2 NAT Gateway độc lập tại 2 Availability Zones (`ap-southeast-1a` và `ap-southeast-1b`).
   - Nhiệm vụ: Cho phép các máy chủ ở Private Subnet kết nối ra Internet để gọi API ngân hàng (VNPay, MoMo),
     gửi email thông báo vé, tải thư viện/Docker image.
   - Tính sẵn sàng cao: Nếu 1 Data Center của AWS bị mất điện, NAT Gateway ở Data Center còn lại vẫn hoạt động.

4. APPLICATION TIER 2 - KONG GATEWAY & CORE MICROSERVICES:
   - Các máy chủ chạy trong Private Subnet, hoàn toàn KHÔNG CÓ Public IPv4 -> Miễn nhiễm 100% với các đòn
     quét port và tấn công trực diện từ Internet.
   - Kong Gateway đóng vai trò Reverse Proxy nội bộ, phân luồng API, mở CORS và Rate-limiting.
   - 5 Microservices Spring Boot 3 / Java 21 kết nối lỏng thông qua Kafka và gRPC.

5. DATA TIER 3 - PERSISTENCE & CACHE CLUSTER (Cách ly tuyệt đối):
   - Multi-AZ RDS PostgreSQL: Nhân bản dữ liệu đồng bộ (Synchronous). Đảm bảo RPO = 0 (Không mất dữ liệu)
     và RTO < 60s (Tự động kích hoạt node Standby thành Master khi có sự cố).
   - Multi-AZ ElastiCache Redis: Tự động bầu chọn (Failover) giữ vững trạng thái khóa ghế và cache.
   - Amazon MSK: Cụm Kafka 3 Brokers phân tán đa vùng, bảo vệ toàn vẹn các sự kiện đặt vé và thanh toán.

BƯỚC 1: TẠO MẠNG 3-TIER MULTI-AZ VPC CHUẨN ENTERPRISE

1.1. Thao tác trên AWS Console:
1. Vào AWS Console -> Region `ap-southeast-1 (Singapore)` -> Dịch vụ **VPC** -> Bấm **Create VPC**.
2. Chọn **VPC and more** (Tính năng tự động sinh topology chuẩn Enterprise):
   - **Name tag**: `cgv-enterprise-vpc`.
   - **IPv4 CIDR block**: `10.0.0.0/16`.
   - **Number of Availability Zones (AZs)**: Chọn `2` (`ap-southeast-1a` và `ap-southeast-1b`).
   - **Number of public subnets**: Chọn `2` (Gán: `10.0.1.0/24` và `10.0.2.0/24`).
   - **Number of private subnets**: Chọn `4` (2 App Subnets: `10.0.10.0/24`, `10.0.11.0/24` và 2 Data Subnets: `10.0.20.0/24`, `10.0.21.0/24`).
   - **NAT Gateways**: Chọn **1 per AZ** (Chuẩn Enterprise High-Availability: Tạo 2 NAT Gateway độc lập).
   - **VPC Endpoints**: Chọn **S3 Gateway** (Cho phép máy chủ đẩy ảnh poster lên S3 miễn phí băng thông).
3. Bấm **Create VPC** -> AWS sẽ tự động tạo VPC, Internet Gateway, 2 NAT Gateways và phân bổ Route Tables cách ly.

1.3. GIẢI THÍCH CHUYÊN SÂU: VÌ SAO LẠI CẦN TỚI TẬN 4 PRIVATE SUBNETS?
Rất nhiều người thắc mắc: "Tại sao không gom lại thành 1 hay 2 Private Subnet mà phải tạo tận 4 cái?"
Lý do nằm ở 2 nguyên tắc kiến trúc cốt lõi của Doanh nghiệp lớn:
- Nguyên tắc 1: High Availability (Đa vùng dự phòng 2 AZs):
  Bạn đang chọn 2 Availability Zones (`ap-southeast-1a` và `ap-southeast-1b`). Mọi tài nguyên chịu lỗi thảm họa (Multi-AZ) bắt buộc phải có mặt đồng thời ở CẢ 2 Data Center. Nếu 1 Data Center gặp sự cố, hệ thống vẫn sống ở Data Center còn lại.
- Nguyên tắc 2: Phân tầng cách ly bảo mật (App Tier vs Data Tier):
  + 2 Subnets dành cho Tầng Ứng Dụng (App Tier):
    * `private1-ap-southeast-1a` (Chứa máy chủ Kong Gateway, Microservices Node 1).
    * `private2-ap-southeast-1b` (Chứa máy chủ Microservices Node 2).
    * Đặc điểm: Cần kết nối ra ngoài Internet (qua NAT Gateway) để gọi webhook VNPay/MoMo, gửi email, gọi API đối tác.
  + 2 Subnets dành cho Tầng Dữ Liệu (Data Tier):
    * `private3-ap-southeast-1a` (Chứa PostgreSQL Master, Kafka Broker 1, Redis Master).
    * `private4-ap-southeast-1b` (Chứa PostgreSQL Standby, Kafka Broker 2, Redis Replica).
    * Đặc điểm: Cách ly tuyệt đối, không có đường ra Internet (ngay cả qua NAT).
    * QUY ĐỊNH BẮT BUỘC CỦA AWS: Khi tạo Amazon RDS Multi-AZ hoặc Amazon MSK, AWS BẮT BUỘC bạn phải chọn tối thiểu 2 Subnet ở 2 AZ khác nhau để làm DB Subnet Group. Nếu không có đủ 2 Subnet ở 2 vùng, AWS sẽ BÁO LỖI KHÔNG CHO TẠO DATABASE!
  => Phép tính: 2 Subnets (Tầng App) + 2 Subnets (Tầng Data) = 4 Private Subnets. Đây là con số tiêu chuẩn vàng!

1.4. GIẢI THÍCH CHUYÊN SÂU: VPC ENDPOINTS LÀ GÌ? VÌ SAO S3 GATEWAY LẠI GIÚP TĂNG TỐC 10X & MIỄN PHÍ 100%?
- Bản chất khi KHÔNG CÓ VPC Endpoint:
  Dịch vụ Amazon S3 (lưu poster phim, trailer) là dịch vụ công cộng của AWS. Nếu máy chủ Java trong Private Subnet muốn upload hoặc tải ảnh từ S3:
  `Máy chủ Java (Private) -> NAT Gateway -> Đi vòng ra Internet -> Amazon S3`.
  + Tốn tiền: NAT Gateway thu phí truyền dữ liệu $0.045/GB. Upload hàng trăm GB ảnh poster sẽ làm hóa đơn NAT tăng vọt.
  + Tốc độ chậm: Gói tin phải đi qua cổng NAT Gateway rồi mới tới S3.
- Khi BẬT "S3 Gateway VPC Endpoint":
  AWS tạo một "Đường hầm cáp quang ảo ngầm" (Private Virtual Link) chạy trực tiếp bên trong hạ tầng vật lý của AWS, nối thẳng từ VPC tới dịch vụ S3.
  `Máy chủ Java (Private) -> Cáp ngầm nội bộ AWS (25 Gbps) -> Amazon S3`.
  + 0 ĐỒNG CHI PHÍ: AWS cung cấp S3 Gateway Endpoint hoàn toàn miễn phí. Toàn bộ lưu lượng sang S3 không bị tính 1 xu tiền NAT Gateway.
  + Tốc độ cực nhanh (Tăng tốc 10x): Chạy trên đường truyền băng thông nội bộ 25 Gbps với độ trễ < 1ms.
  + Bảo mật tuyệt đối: Dữ liệu nội bộ không bao giờ phải đi ra mạng Internet công cộng.

1.5. GIẢI NGHĨA TOÀN BỘ SƠ ĐỒ PREVIEW TRÊN MÀN HÌNH AWS CONSOLE (TỪ TRÁI SANG PHẢI):
Quan sát 4 cột trong sơ đồ Preview của AWS Console:
[ Cột 1: VPC ] -> [ Cột 2: Subnets (6) ] -> [ Cột 3: Route Tables (5) ] -> [ Cột 4: Network Connections (3) ]

- Cột 1: `VPC (cgv-enterprise-vpc-vpc)`:
  Đại diện cho toàn bộ "vùng mạng riêng" độc lập của dự án CGV trên đám mây AWS.
- Cột 2: `Subnets (6)` (Chia đều 2 Data Center):
  + Ở `ap-southeast-1a`:
    * `subnet-public1`: Chứa Load Balancer Node A và NAT Gateway 1.
    * `subnet-private1`: Chứa Microservices Java Node 1.
    * `subnet-private3`: Chứa PostgreSQL Master, Kafka Broker 1, Redis Master.
  + Ở `ap-southeast-1b`:
    * `subnet-public2`: Chứa Load Balancer Node B.
    * `subnet-private2`: Chứa Microservices Java Node 2.
    * `subnet-private4`: Chứa PostgreSQL Standby, Kafka Broker 2, Redis Replica.
- Cột 3: `Route Tables (5)` (Bảng chỉ đường phân luồng giao thông):
  AWS tự động sinh ra 5 bảng chỉ đường riêng biệt:
  + `rtb-public`: Bảng chỉ đường cho 2 Public Subnet.
  + `rtb-private1`, `rtb-private2`, `rtb-private3`, `rtb-private4`: Bảng chỉ đường riêng cho từng Private Subnet để kiểm soát chiều đi của dữ liệu.
- Cột 4: `Network Connections (3)` (Các cổng xuất nhập cảnh):
  Nhìn các đường dây nối từ Route Table sang Network Connections:
  1. `cgv-enterprise-vpc-igw` (Internet Gateway):
     * Chỉ có đường kẻ từ `rtb-public` nối tới đây!
     * Ý nghĩa: Chỉ có Public Subnet mới được giao tiếp trực tiếp 2 chiều với Internet.
  2. `cgv-enterprise-vpc-nat-public1-ap-` (NAT Gateway):
     * Các đường kẻ từ `rtb-private` nối vào đây!
     * Ý nghĩa: Các máy chủ trong Private Subnet khi cần gọi ra Internet (VNPay, MoMo) sẽ đi "nhờ" qua cổng NAT Gateway này (chỉ ra được 1 chiều, bên ngoài không chọc vào được).
  3. `cgv-enterprise-vpc-vpce-s3` (S3 Gateway Endpoint):
     * Các đường kẻ từ `rtb-private` cũng đồng thời nối thẳng vào đây!
     * Ý nghĩa: Khi có lệnh tải ảnh poster phim từ S3, Route Table sẽ bẻ nhánh gói tin đi thẳng qua cổng cáp ngầm nội bộ này tới S3 mà không cần qua NAT Gateway.

💡 CÂU HỎI KỸ THUẬT: "ĐÂY LÀ QUY ƯỚC HAY AWS TỰ GÁN? CÓ THIẾT LẬP NÀO GÁN PRIVATE 1 & 2 CHO APP CHƯA?"
1. Bản chất: Đây là QUY ƯỚC KIẾN TRÚC (Architectural Convention) chuẩn quốc tế. Bản thân AWS không tự ép subnet nào phải chạy App hay DB, mà do Kỹ sư Cloud phân bổ và gán vai trò khi tạo từng tài nguyên.
2. Thứ tự thiết lập thực tế trong dự án:
   - Bước 1 (Tạo VPC): Chỉ mới "chia lô đất trống" thành 6 Subnets, chưa cắm bất kỳ máy chủ nào vào.
   - Bước 2 (Security Groups): Chỉ mới tạo các "thẻ bài tường lửa", chưa áp vào máy chủ nào.
   - Bước 3 (NGAY LÚC NÀY - RDS): Đây là bước ĐẦU TIÊN bắt đầu phân đất! Ta tạo "DB Subnet Group" và chọn `private3` & `private4` để ra lệnh cho RDS: Toàn bộ máy chủ Database chỉ được phép nằm ở 2 subnet này.
   - Bước 4 (Tạo EC2 Backend): Khi bấm tạo EC2, AWS sẽ hỏi "Đặt EC2 ở Subnet nào?", ta sẽ CHỦ ĐỘNG chọn `private1` và `private2`.
   - Bước ALB (Load Balancer): AWS hỏi "ALB đón khách đặt ở đâu?", ta sẽ CHỦ ĐỘNG chọn `public1` và `public2`.
3. Vì sao tách biệt App (`private1, 2`) và Data (`private3, 4`)?
   - Phòng thủ chiều sâu (Defense-in-Depth): Giả sử 1 container web bị hacker chiếm quyền, hacker không thể quét trực tiếp mạng LAN của Database vì 2 tầng nằm ở 2 dải IP khác nhau.
   - Quản lý Route Table độc lập: App cần ra Internet qua NAT Gateway để gọi VNPay/MoMo/gửi mail vé, trong khi Database tuyệt đối CẤM ra ngoài Internet.

     + Tại `ap-southeast-1a`: Chọn `cgv-enterprise-vpc-subnet-private3-ap-southeast-1a` (`10.0.160.0/20`)

   - Availability and durability (Deployment options):
     + **Multi-AZ DB Instance / Cluster**: Dành cho môi trường doanh nghiệp có trả phí (tính sẵn sàng 99.99%).

     + Gói Doanh nghiệp lớn: Chọn `db.m6g.large` hoặc `db.t4g.medium`.
   - Storage:
     + Gói Free Tier: `20 GiB gp3` (nằm trong hạn mức miễn phí của AWS).
     + Gói Doanh nghiệp: `100 GiB gp3`, tích chọn **Enable storage autoscaling**.
   - Connectivity (Kết nối mạng — Cực kỳ quan trọng):

     + DB subnet group: Chọn `cgv-rds-data-subnet-group` vừa tạo.
     + Public access: Chọn **No** (Khóa cứng cơ sở dữ liệu trong mạng kín an toàn 100%).
     + VPC security group: Chọn `Choose existing` -> Chọn `cgv-db-sg` (xóa group `default`).
   - Additional configuration:
     + Initial database name: Gõ chữ **`cgv`** (để PostgreSQL tự sinh DB tên `cgv` cho Backend).
     + Enable deletion protection: Để **Unchecked** (không tích) ở môi trường Test/Dev để thuận tiện dọn dẹp lab sau này.
   - Bấm **Create database** -> Đợi chuyển sang trạng thái `Available` (mất khoảng 5-7 phút) -> Copy **Endpoint**.

9.1. GIẢI THÍCH BẢN CHẤT LỖI VÀ VÌ SAO PHẢI DÙNG ECR (KHÔNG THỂ DÙNG DOCKER LOCAL):

1. Vì sao có lỗi ImagePullBackOff / ErrImagePull?
   - Khi K8s chạy các Pod microservice (booking-service, identity-service,...), file deployment.yml
     ban đầu ghi `image: cgv/booking-service:latest`.
   - Các Pod chạy trên các máy chủ EC2 tại Singapore (AWS Cloud). Khi chúng tìm kiếm `cgv/*:latest`,
     mặc định K8s sẽ lên mạng internet công cộng (Docker Hub: docker.io) để tải về.
   - Do `cgv/*` là code dự án nội bộ của bạn (chỉ nằm trên máy tính cá nhân), Docker Hub không hề có
     và trả về lỗi: `insufficient_scope: authorization failed / repository does not exist`.

2. Phân biệt Docker Local vs Amazon ECR vs Amazon EKS:
   - DOCKER LOCAL (Máy tính của bạn / CI Server): Là "Xưởng sản xuất". Nhiệm vụ là đọc mã nguồn Java,
     thực hiện lệnh `docker build` để đóng gói thành Docker Image.
   - AMAZON ECR (Elastic Container Registry): Là "Kho tổng lưu trữ trên đám mây". Đây là kho chứa Docker
     riêng tư, bảo mật 100% của riêng tài khoản AWS của bạn (Account ID: 313078327818).
     ECR không tự biên dịch code, mà nó chờ bạn hoặc CI/CD `docker push` các image lên đây cất giữ.
   - AMAZON EKS (Kubernetes Cluster): Là "Nhà máy vận hành". EKS sẽ tự động kéo (pull) các Docker Image
     từ kho ECR về các máy ảo EC2 để chạy thành các Pods phục vụ người dùng.

3. Các lỗi hạ tầng đã được tự động xử lý thành công:
   - Lỗi Kong Gateway: Tag cũ ghi `kong:3.4-alpine` (Docker Hub đã bỏ tag alpine cho bản 3.x),
     đã chuyển thành `kong:3.4` -> Kong Gateway đã chuyển sang trạng thái 1/1 RUNNING (XANH 100%).
   - Lỗi Kafka Brokers: Kafka KRaft mode yêu cầu RAM khởi tạo LogCleaner tối thiểu 256MB-512MB.
     Cấu hình cũ để Heap 180MB gây lỗi `OutOfMemoryError: Java heap space`. Đã nâng cấp Heap lên
     `-Xmx512m -Xms256m` và RAM limit 750Mi -> Cả 3 Broker Kafka (kafka-1, kafka-2, kafka-3)
     đều đã chuyển sang trạng thái 1/1 RUNNING (XANH 100%).

CHƯƠNG 11: BƯỚC TIẾP THEO: CẤU HÌNH CLOUDFRONT (HTTPS) VÀ AWS WAF
================================================================================
TẠI SAO BẮT BUỘC PHẢI LÀM BƯỚC NÀY?
1. Lỗi Mixed Content: Khi Frontend deploy lên Vercel, Vercel luôn chạy HTTPS (https://...).
   Nếu gọi backend qua HTTP thô của NLB (http://k8s-cgvprod-kongprox...), trình duyệt Chrome/Safari
   sẽ CHẶN TOÀN BỘ API vì vi phạm Mixed Content (Failed to fetch)!
2. Cố định URL: Địa chỉ NLB của AWS rất dài. CloudFront giúp tạo domain HTTPS cố định
   (https://dXXXXXXXXX.cloudfront.net hoặc domain riêng https://api.yourdomain.com).
3. Tường lửa AWS WAF: Bảo vệ rạp chiếu phim khỏi bot spam đặt vé ma, quét lỗ hổng SQLi, XSS.

--------------------------------------------------------------------------------
11.1. CÁC BƯỚC TẠO CLOUDFRONT DISTRIBUTION TRÊN GIAO DIỆN WIZARD MỚI (4 BƯỚC):
--------------------------------------------------------------------------------
Vào AWS Web Console -> Tìm kiếm dịch vụ 'CloudFront' -> Bấm nút màu cam 'Create distribution'.

BƯỚC 1: Get started / Distribution details (Chi tiết ban đầu)
1. Distribution name: Nhập 'cgv-api-cdn'
2. Distribution type: Giữ nguyên mặc định "Single website configuration".
3. Route 53 managed domain - optional: ĐỂ TRỐNG (AWS sẽ tự cấp domain HTTPS *.cloudfront.net miễn phí).
4. Bấm nút màu cam 'Next'.

BƯỚC 2: Specify origin (Cấu hình nguồn Backend Kong NLB)
1. Origin type: Tích chọn ô "Elastic Load Balancer".
2. Elastic Load Balancing origin: Dán hoặc chọn đúng DNS của Kong NLB:
   k8s-cgvprod-kongprox-b0dc6588ff-c408e1f3fa455726.elb.ap-southeast-1.amazonaws.com
3. Origin path - optional: Để trống.
4. Settings:
   • Origin settings: Giữ nguyên "Use recommended origin settings".
   • Cache settings: Giữ nguyên "Use recommended cache settings tailored to serving Elastic Load Balancing content".
5. Bấm nút màu cam 'Next'.

BƯỚC 3: Enable security (Tường lửa WAF & Chi phí)
LƯU Ý CỰC KỲ QUAN TRỌNG VỀ CHI PHÍ:
• Nếu chọn "Enable security protections": AWS WAF sẽ bật tường lửa chống DDoS Layer 7, SQLi, Rate limit... nhưng AWS CÓ THU PHÍ (ước tính khoảng ~$37.5 / tháng cho WAF).
• Nếu chọn "Do not enable security protections": Hoàn toàn MIỄN PHÍ ($0) trong gói AWS Free Tier. CloudFront vẫn cấp HTTPS cực kỳ an toàn, giải quyết 100% lỗi Mixed Content.
👉 KHUYẾN NGHỊ:
Tích chọn ô bên phải: "Do not enable security protections" (để không phát sinh chi phí). Sau này khi có nhu cầu lên Production thực thụ, bạn có thể bấm bật WAF bất kỳ lúc nào.
Bấm nút màu cam 'Next'.
